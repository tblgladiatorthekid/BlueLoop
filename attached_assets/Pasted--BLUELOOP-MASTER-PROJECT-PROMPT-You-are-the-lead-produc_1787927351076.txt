# BLUELOOP MASTER PROJECT PROMPT

You are the lead product architect, senior full-stack engineer, UX designer, data engineer, and technical strategist working with me to build **BlueLoop**, a software-first marine-litter recovery platform for the Protego Blue Innovation Challenge Hackathon.

## 1. PROJECT CONTEXT

BlueLoop is being developed as a pilot project for **Eleko Beach, Lagos, Nigeria**.

The problem we are addressing is marine litter, particularly plastic waste. The core problem is not simply that waste exists, but that there is weak coordination between:

* people who encounter and collect recyclable waste;
* communities and beach users;
* waste collection points;
* recycling organizations;
* organizations attempting to reduce marine pollution.

BlueLoop aims to create an incentive-driven digital network that makes marine-litter recovery easier to participate in, easier to verify, easier to measure, and easier to connect to recycling.

The system has two closely integrated concepts:

### BlueLoop

The overall marine-litter recovery and coordination platform.

### BlueBank

The incentive, rewards, transaction and verification layer within BlueLoop.

The initial MVP MUST be software-first.

Do NOT make physical waste-interception hardware a requirement for the MVP. Physical interventions such as drainage or waterway litter traps may appear in the long-term roadmap, informed by data generated by BlueLoop.

---

# 2. CORE PRODUCT VISION

BlueLoop should create the following loop:

**Recover → Verify → Reward → Record → Aggregate → Recycle → Measure Impact → Expand**

A participant collects recyclable material.

A participating collection point verifies the material and records its weight and type.

BlueBank rewards the participant.

The material enters the collection/recycling chain.

BlueLoop aggregates the data.

The data identifies:

* quantities of waste recovered;
* types of waste;
* collection patterns;
* recurring hotspots;
* participation;
* recycling outcomes.

As the network expands, this data can help environmental organizations, recyclers, communities and relevant authorities make better decisions about marine-litter intervention.

The long-term vision is to transform BlueLoop from a single-beach pilot into a distributed coastal waste-recovery network.

---

# 3. MVP OBJECTIVE

The MVP should answer one fundamental question:

> Can a digital platform successfully incentivize, coordinate and track community-based recovery of recyclable marine litter while connecting recovered materials to recycling partners?

The MVP should therefore prioritize VALIDATION over feature quantity.

Do not build unnecessary features simply because they sound impressive.

The MVP should demonstrate:

1. Participant registration
2. Collector/user profiles
3. Collection-point registration
4. Waste submission/collection recording
5. Material categorization
6. Weight recording
7. Verification by authorized collection operators
8. BlueBank reward calculation
9. Participant reward balance
10. Collection history
11. Collection-point discovery
12. Recycling partner records
13. Basic impact dashboard
14. Eleko Beach hotspot/location data
15. Administrative controls
16. Basic analytics

---

# 4. PRIMARY USER TYPES

Design the system around these roles:

## A. Participant / Collector

A resident, fisherman, beach worker, student, visitor or informal collector who recovers recyclable waste.

They should be able to:

* create an account;
* view their BlueBank balance;
* submit collected material;
* see collection history;
* see rewards earned;
* find collection points;
* view their contribution to marine-litter recovery.

## B. Collection Point Operator

An individual or organization authorized to verify submitted material.

They should be able to:

* authenticate;
* record a collection;
* identify participant;
* select material type;
* enter verified weight;
* submit evidence if appropriate;
* confirm the transaction;
* view collection history;
* view accumulated materials awaiting transfer.

## C. Recycling Partner

A recycling organization receiving aggregated recyclable materials.

They should be able to:

* manage organization information;
* define accepted materials;
* view available material;
* record material transfers;
* confirm receipt;
* provide recycling/outcome data where possible.

## D. Administrator

BlueLoop administrators should be able to:

* manage users;
* approve/reject collection points;
* approve recycling partners;
* manage reward rules;
* monitor suspicious transactions;
* view system-wide analytics;
* manage waste categories;
* view hotspot information;
* manage platform configuration.

Do not give users permissions they do not need.

---

# 5. BLUEBANK REWARD SYSTEM

BlueBank should NOT simply give arbitrary points.

Design a configurable reward system based on:

* material type;
* verified weight;
* current pilot reward rates;
* potentially quality/contamination;
* optional bonus campaigns.

The reward engine should be configurable by administrators.

For example:

PET may have one reward rate per kilogram while aluminum, HDPE or other materials have different rates.

Do NOT hardcode economic assumptions into the architecture.

Reward rates should be stored as configuration/data.

Every reward transaction should have:

* unique transaction ID;
* participant;
* collection point;
* material type;
* verified weight;
* reward amount;
* timestamp;
* verification status;
* operator;
* optional evidence;
* audit history.

Treat the reward ledger as financially sensitive data even if the pilot uses non-cash credits.

Prevent duplicate or manipulated transactions.

---

# 6. VERIFICATION

Verification is a critical part of BlueLoop.

A participant should not be able to claim:

> "I collected 50 kg."

and magically receive 50 kg worth of rewards.

The collection point operator should verify the material.

The system should distinguish between:

* pending;
* verified;
* rejected;
* cancelled/reversed.

Consider mechanisms such as:

* operator authentication;
* unique transaction IDs;
* timestamps;
* collection-point identity;
* participant identity;
* optional photographs;
* location data where appropriate;
* audit logs.

Keep the MVP verification system simple enough to actually deploy.

---

# 7. WASTE CATEGORIES

The system should support configurable waste categories.

Initial examples:

* PET bottles
* HDPE
* plastic bags/nylon
* food packaging
* fishing-related plastics
* aluminum
* other recyclable materials
* non-recyclable material

Do not assume these categories are final.

The data model should allow administrators to add or modify categories without changing application code.

---

# 8. COLLECTION POINT NETWORK

BlueLoop should provide a way to discover participating collection points.

Each collection point should contain:

* name;
* location;
* coordinates;
* address/description;
* operating status;
* accepted materials;
* operator;
* verification status;
* operating hours if applicable.

The system should be designed so additional collection points can be added as BlueLoop expands beyond Eleko Beach.

Eleko Beach is the PILOT, not the permanent geographic limitation of the application.

Avoid hardcoding Eleko-specific logic into the platform.

---

# 9. HOTSPOT AND IMPACT DATA

BlueLoop should collect useful environmental data without creating unnecessary surveillance.

Useful data includes:

* collection location;
* collection date;
* waste type;
* weight;
* number of collections;
* participating collectors;
* recurring collection locations.

The platform should eventually visualize:

* total waste recovered;
* waste recovered by category;
* recovery over time;
* active participants;
* collection points;
* major accumulation areas;
* recycling transfers;
* estimated environmental impact.

The architecture should leave room for future GIS functionality.

However, DO NOT over-engineer a sophisticated AI prediction system into the MVP.

A reliable basic map and dashboard are more valuable than an impressive but unvalidated machine-learning model.

---

# 10. PRIVACY

Collect only information necessary for the pilot.

Avoid unnecessary collection of:

* precise personal information;
* sensitive information;
* continuous location tracking;
* unnecessary photographs;
* unnecessary demographic data.

Location information should primarily describe collection/activity locations rather than continuously tracking participants.

Design the system with privacy and data minimization in mind.

---

# 11. SCALABILITY REQUIREMENTS

The architecture must support the following progression:

### Stage 1

Eleko Beach pilot

### Stage 2

Multiple collection points around Eleko and neighboring communities

### Stage 3

Other coastal communities in Lagos

### Stage 4

Other Nigerian coastal cities

### Stage 5

Regional expansion across West African coastal communities

Do not build separate applications for each location.

Use a multi-location architecture in which:

* locations are data;
* collection points are data;
* organizations are data;
* reward schemes are configurable;
* waste categories are configurable;
* users can belong to organizations/locations;
* administrators can manage different operational areas.

The application should be capable of growing without requiring a rewrite.

---

# 12. RECYCLING PARTNERSHIPS

BlueLoop does NOT need to own recycling facilities.

Design the system around partnerships.

The platform should eventually support:

**Participant → Collection Point → Aggregation → Recycling Partner**

A recycling partner should be able to confirm receipt of material.

This allows BlueLoop to measure:

> collected → verified → transferred → received/recycled

rather than claiming that every kilogram collected was automatically recycled.

Never fabricate recycling impact.

# 13. BUSINESS MODEL

The long-term platform should potentially support several revenue streams:

* partnerships with recycling companies;
* corporate sponsorship;
* environmental/EPR programs;
* municipal partnerships;
* platform/service contracts;
* sponsored collection/reward campaigns;
* value generated through aggregated recyclable materials.

The MVP does NOT need to implement every revenue model.

Instead, structure the platform so these models can be incorporated later.

Do not introduce monetization complexity that interferes with validating the core recovery model.

# 14. TECHNICAL APPROACH

Before writing code, inspect the existing development environment and recommend an appropriate architecture.

I am a Computer Science undergraduate and want the system to be technically credible but realistically buildable within a hackathon timeline.

Prioritize:

* maintainability;
* security;
* clear architecture;
* low operational cost;
* easy deployment;
* mobile responsiveness;
* good developer experience;
* scalability.

A PWA/web-first approach is acceptable if it gives us the fastest path to a usable field prototype.

Do not select technologies merely because they are fashionable.

If an existing technology in the project is already suitable, use it instead of replacing everything.

---

# 15. UX PRINCIPLES

The platform will potentially be used by people who are not highly technical.

Therefore:

* minimize unnecessary steps;
* use clear language;
* make the collection workflow fast;
* make reward balances obvious;
* make verification status understandable;
* design for mobile first;
* account for potentially poor network conditions;
* avoid overly complicated dashboards for ordinary users.

The collection operator workflow should ideally take less than a minute for a routine transaction.

---

# 16. FIELD REALITY

This is a real pilot at Eleko Beach, not merely a portfolio application.

Whenever proposing functionality, ask:

> Can this realistically be used by a person standing at a collection point at Eleko Beach using a smartphone?

Consider:

* intermittent connectivity;
* limited technical literacy;
* battery constraints;
* operator workload;
* fraud;
* incorrect weight entries;
* duplicate transactions;
* unreliable data;
* participant trust;
* incentive abuse.

The system should degrade gracefully when connectivity is poor.

If full offline functionality is too complex for the MVP, design at least for graceful retry and transaction recovery.

---

# 17. SECURITY

Treat authentication, authorization and reward transactions seriously.

Implement:

* secure authentication;
* role-based authorization;
* server-side validation;
* input validation;
* protected administrative functions;
* audit logging for important actions;
* secure handling of credentials/secrets;
* prevention of unauthorized reward manipulation.

Never trust client-side reward calculations.

All important reward and verification calculations must be validated server-side.

---

# 18. ANTI-FRAUD

Consider realistic abuse cases:

* fake collection submissions;
* duplicate submissions;
* collusion between participant and operator;
* manipulated weights;
* fake collection points;
* unauthorized reward adjustments;
* account sharing.

Do not attempt to solve every fraud problem with AI.

Start with simple controls:

* authenticated operators;
* unique transactions;
* audit logs;
* verification states;
* reasonable transaction limits;
* anomaly flags;
* administrator review.

Build more sophisticated fraud detection only if the pilot generates enough data to justify it.

# 22. HACKATHON DEMONSTRATION

The final MVP should support a compelling live demonstration.

The ideal demo flow is:

1. A participant logs into BlueLoop.
2. They see their BlueBank balance.
3. They bring recyclable material to a collection point.
4. The operator records the material and weight.
5. The transaction is verified.
6. BlueBank automatically calculates the reward.
7. The participant sees their updated balance.
8. The dashboard updates the total recovered waste.
9. The material appears in the collection point's inventory.
10. A recycling partner can eventually confirm receipt.
11. The admin dashboard displays the broader impact.

The demo should tell a complete story:

**person → waste → verification → reward → recycling → measurable impact.**
